01 · Before dawn · Phase 1, before Arla

The brand changed, and Material UI could not follow it. So we built our own library.

My partMain contributor on a team of four: audit, tokens, component design, the Figma library, and a vibe-coded button style.

Material UI made sense at the start: a complete set of components and patterns teams already understood. After the rebrand, every custom override meant fighting its styling. We chose React Aria, an open-source toolkit from Adobe, for behaviour: it handles how components work for keyboard, touch and screen-reader users, and leaves the look to us. Colour, spacing and typography were built from the brand guidelines, and icons came from Lucide.

What I built, and where it went

I audited what the product used, defined the tokens, designed the components, built the Figma library, and vibe coded a new button style myself, submitted for engineers to review. Every token and component shipped to production.

03 · Plumage · Semantic tokens

Feathers with a job. Each token is named for what it does, so AI agents can use it as well as people.

My partDefining the token rules, as a secondary contributor with a lead designer and a lead engineer.

Each token is named by its role, limited to the one use it is meant for (a text colour can only go on text), and carries a one-line description. The generated docs list every token's name in code beside its Figma name, its value and that description, so an agent writing code has the same information a designer would use to choose it.

Arla · PlumageToken rules

badge/error/background-strong

Lowercase, slash-separated, general to specific. Four segments at most.

Never a hue name in a semantic token

Use badge/error/*, not badge/chili/*.

Group
badge/
The area or component the role belongs to.
Variant
error/
Optional. Sentiment or component variant, named by role.
Property
background
What the token styles: background, border, text, icon or stroke.
State or emphasis
-strong
A hyphenated suffix: default, hover, pressed, focus, disabled, strong.

The questions to ask before adding a token. The goal is a small set of specific roles.

QuestionDo thisWhy
A semantic token already resolves to this value in this role?Reuse it.Same role and same value means no new token.
Same value, different role?Create a new role token.Roles that match today can diverge later, as surface/default and surface/raised may.
Used by one component only?Create it in that component group, such as tag/border-focus.Keeps roles specific and easy to retire.
Used by two or more components?Create it in a shared group, such as status/warning-border.Avoids duplicate tokens for one meaning.
Only a primitive fits?Add the semantic role first, then bind to it.Components never bind to primitives.

05 · Flight · Code and releases

Automated checks (the build) run before any change is accepted, so no reviewer has to remember the rules.

Figma-driven tokens

Tokens are generated from Figma Variables, so design and code cannot drift apart by hand-editing. Components can only use tokens named by their purpose.

Build fails if a component has a colour or size typed in directly.

Accessibility by default

Every component is built on React Aria, the accessible toolkit. Each has an automated accessibility check and keyboard tests.

Build fails if a component uses the browser’s bare button, text field or dropdown instead.

Generated docs

Tables of each component’s options, and of which Figma name matches which code name, are produced automatically. Every component needs a usage guide.

Build fails if any part of a component’s documentation is missing.

Careful releases

Every version of a component must have its own live preview page (a “story”) in the documentation site. Each release comes with a written record of what changed.

Build fails if a version of a component has no preview page.
